Core: Experimental: a workflow can commit the stream records it published with the new `WorkflowOutputStreamCommit` command, each with its plaintext content hash and size. Core builds the output manifest from them and records it in a `core_external_stream` marker ahead of the completion's other commands. While replaying, lang commits the same records again without bodies, and Core checks the manifest it builds from them against the recorded one (the run id and store name aside), or the task fails as nondeterministic. A workflow that wrote this marker can only move forward. A Worker on an older Core, or one whose lang doesn't commit the records again on replay, fails that workflow's next task, so don't roll such a fleet back.
Core: Experimental: behind the new `streams` feature, `WorkerConfig::stream_store` takes the store a workflow's stream output goes to. Core appends each activation's records to it when the activation completes, before the workflow task completes, as the run's producer `@<run id>`. The producer attempt rises only after a workflow task failed or timed out, so readers see one supersession when a task runs again. Core fails the workflow task when the store refuses the records or the Worker has none.
Core: Experimental: Core closes the stream topics a workflow task closed once the server accepts the completion, in commit order, with each close's result. A task the server refuses closes nothing, so its rerun can still publish. When the answer is lost, Core closes only what the next replay finds in History.
Core: Experimental: after a workflow's final task (complete, fail or cancel, not continue-as-new) is accepted, Core closes its run chain's streams in the store, so readers end and producers are refused. It waits for the run's topic closes and checks the chain's latest run first, and leaves the streams open for a retry or cron successor. A failed close is retried with backoff until it lands or the Worker stops.
