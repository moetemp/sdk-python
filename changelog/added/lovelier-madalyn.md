Experimental: progress of a started Nexus operation reaches lang in the Workflow Task attachments job, as `Any(NexusOperationProgress)` keyed by endpoint, service, operation and token. The Workflow folds a task's progress to the highest counter per key and gives it to each started, unresolved operation with that key. Progress for an operation that is unknown, not started, already resolved, or at or below a counter already delivered is dropped. Replay delivers the same attachments in the same activations.
Core: Experimental: the stream calls `AttachCaller` and `DetachCaller` serve a stream-returning Nexus operation. `AttachCaller` resolves the stream's run chain, mints the operation token and attaches the start's callback to the stream's notifier with the token and start time. `DetachCaller` decodes the token and detaches from the chain the start attached to. The token format is in `crates/streams/nexus/operation_token_vectors.json`, which every SDK's encoder and decoder check. Both answer a failure in the response as a `NexusFailure`, from the same table as the Nexus calls, so lang's handler raises it as it is. A mistake in the stream, an empty callback URL or request id, and a token that names no stream are `BAD_REQUEST`. An attach for the latest run describes the Workflow fresh, so it never lands on a chain that already ended.
Core: Experimental: `AttachCaller` attaches the caller's callback as an idle one, which hears no progress until a wait after a counter and still gets the completion. A reader reads first, so a busy one costs no deliveries. `NotifierClient::wait_callback` sends the new `WaitStreamCallback`, and the C bridge takes it as a raw call. The API protos carry the `NexusHandler` progress fields and `nexus/notification-service.wit`.
