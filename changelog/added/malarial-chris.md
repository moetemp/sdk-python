Core: Experimental: progress of a started Nexus operation reaches lang as a `ResolveNexusOperationProgress` job, at most one per operation per workflow task, with the highest counter the server folded onto the task's scheduled event. Replay delivers the same jobs in the same activations. Progress for an operation that is unknown, not started, already resolved, or below a counter already delivered is dropped.
Core: Experimental: with `StreamStoreConfig.notify_on_append`, Core tells each stream's notifier on the server when the stream moves while a reader sleeps on it. That's how a caller of a stream-returning Nexus operation sees progress. A reader arms the stream with a read that sets the new `ReadRequest.arm` (Nexus `ReadInput.arm`) and waits its whole wait with no record. The answer says `armed`, and the next append or Workflow batch that becomes visible notifies once. Core clears the arm once the notification lands, and a failed one keeps it for the next write. A busy stream, whose readers find records on each read, sends no notification, apart from one refresh a day that keeps its notifier from the idle timeout. An attach to an empty stream arms it, so the first append reaches the new caller. `notify_every_append` restores a notification after every write, for readers that can't arm. Notifications for one stream fold into one call in flight, a failed last notification is tried twice more, and a notification never fails the write. `max_notifiers` caps how many streams the process keeps a notifier for (1000 when zero).
Core: Experimental: the new `FlushNotifications` stream call waits up to 10 seconds for the notifications still out. A Worker flushes at stop on its own, so only a process that holds just a client needs it.
Core: Experimental: a server without the stream notifier answers the first notifier call with `UNIMPLEMENTED`. Core then stops notifier calls in that process and logs it once at debug.
Core: Experimental: Core closes a stream's notifier after the store closes the stream, whether or not `notify_on_append` is on, so attached operations complete with the close result. A Workflow's topic close and a `CloseRequest` with the new `result` field carry the result. A `CloseRequest` with a result fails when the server doesn't take the close, and Core keeps trying in the background too. When a publishing Workflow's chain ends, its Worker closes the notifier of every topic the store still lists as open, with an empty result. A reader that finds the owner ended closes only the store, since the server keeps the first close.
Core: Experimental: `StreamStore` has `open_topics`, `end_chain` and `close_stream`. The Redis store keeps a topic set per chain for `open_topics`, which needs `+sadd` and `+smembers` in the ACL. Without them, writes still work and the store logs a warning once, but a chain end can't close every notifier. Widen the ACL with the upgrade.
Core: Experimental: the stream calls `AttachCaller` and `DetachCaller` serve a stream-returning Nexus operation. `AttachCaller` resolves the stream's run chain, mints the operation token and attaches the start's callback to the stream's notifier with the token and start time. `DetachCaller` decodes the token and detaches from the chain the start attached to. The token format is in `crates/streams/nexus/operation_token_vectors.json`, which every SDK's encoder and decoder check. Both answer a failure in the response as a `NexusFailure`, from the same table as the Nexus calls, so lang's handler raises it as it is. A mistake in the stream, an empty callback URL or request id, and a token that names no stream are `BAD_REQUEST`. An attach for the latest run describes the Workflow fresh, so it never lands on a chain that already ended.
